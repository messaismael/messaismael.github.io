# i18n — paraglide-js

> Convention technique

**Quoi** : tout texte affiché à l'utilisateur (titres, paragraphes, labels de
nav, CTA, aria-label) passe par paraglide-js — jamais de chaîne de caractères
en dur dans un composant `.svelte`.

- Sources de traduction : `messages/en.json` (locale de base) et
  `messages/fr.json`, format `inlang-message-format`.
- Usage dans un composant : `import { m } from '$lib/paraglide/messages.js';`
  puis `{m.ma_cle()}` (ou `m.ma_cle({ param })` pour les messages avec
  placeholders).
- La compilation `messages/*.json` → `src/lib/paraglide/` est automatique via
  le plugin Vite (`paraglideVitePlugin`), déclenchée dès que les fichiers
  source changent en dev.

**Stratégie de locale — cookie, pas préfixe d'URL** : ce projet utilise la
stratégie par défaut `["cookie", "globalVariable", "baseLocale"]`
(`src/lib/paraglide/runtime.js`). Il n'y a **pas** de route `/fr/...` —
visiter `/fr` ne change rien. Le changement de langue se fait via
`setLocale('fr')` côté client (pose un cookie `PARAGLIDE_LOCALE`), voir
`src/routes/demo/paraglide/+page.svelte` pour l'exemple.

**Limite volontaire — ce qui n'est pas traduit** : noms propres (« Ismael
Messa », « Hermes AI ») et noms de technologies (« Spring Boot »,
« LangGraph »...) restent identiques dans les deux locales par nature — ils ne
passent pas par des clés `m.xxx()` dédiées. Les compteurs purement numériques
(`01/04`) ne sont pas non plus traduits.

**Comment l'appliquer** :

1. Ajouter la clé dans `messages/en.json` **et** `messages/fr.json` (jamais
   une seule des deux).
2. Choisir un nom de clé descriptif du contenu, préfixé par sa zone
   (`hero_*`, `nav_*`, `case_study_*`...).
3. Utiliser `m.<clé>()` dans le composant, jamais la chaîne brute.

⚠️ **Écart connu** : la route `/demo/paraglide` (scaffold par défaut de
SvelteKit) montre encore l'ancienne clé `hello_world` — pas un problème, c'est
la page de démo du template, pas du contenu produit.
